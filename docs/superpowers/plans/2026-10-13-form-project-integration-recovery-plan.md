# フォームメーカーと企画ツールの連携復旧計画

> 実行時は `superpowers:executing-plans` に沿って各段階を順に進める。本書は計画だけであり、実装・Apps Script編集・フォーム作成・push・公開を開始する指示ではない。

**Goal:** フォームメーカーから作った応募フォームの回答が、対応する企画の応募者一覧へ自動反映される既存の仕組みを復旧し、履歴・テーマ・参加者確定・後続の割当と精算を保つ。

**Architecture:** 変更前後のApps Script接続先と公開ソースを照合し、既存の連携処理を持つ正しいアプリを特定する。フォーム作成、企画との関連付け、回答送信、Firebaseへの反映、企画画面の受信という経路を順に確認して、途切れた箇所だけを修正する。現在の単体フォームメーカーを正しい基盤と決めつけない。

**Tech Stack:** Google Apps Script / Google Forms、Firebase Realtime Database、既存のReact / Carbonアプリ、Vite、Node.js、Playwright、GitHub Actions / Pages。

**Spec:** このチャットの必須要件「応募者の回答を企画ツールへ自動で取り込む」と「今回は計画だけ」を本書の成功条件へ具体化する。過去の [履歴連携復旧計画](2026-10-13-apps-script-history-bridge-recovery-plan.md) は参考資料であり、回答連携の完了を証明するものではない。

## 1. 目指す利用の流れ

1. 担当者がフォームメーカーで企画の応募フォームを作る。
2. 作成したフォームと対応する企画が確実に関連付く。新しい企画を生成するか、既存企画に結び付けるかは、以前の正常版の仕様を確認して決める。
3. 応募者がGoogleフォームへ回答する。
4. 担当者がCSVを手作業で取り込まなくても、その企画の応募者一覧へ回答が反映される。
5. 担当者が応募者から参加者を選び、確定する。応募の受信だけで全員を参加確定にしない。
6. その後の車割り、班分け、精算、提出用データ作成が従来どおり使える。
7. ポータルのフォーム履歴から応募フォームと対応企画を開ける。

企画名の入力補助や元画面へ戻るリンクだけでは、この計画の成功条件を満たさない。

## 3. 復旧方針の比較

| 方針 | 利点 | 課題 | 採否 |
| --- | --- | --- | --- |
| 正常だった連携版を特定し、必要な履歴・テーマ修正を移す | 既存の回答・企画・権限の契約を保ちやすい。修正範囲を小さくできる | 正常版の全ソースと公開設定の取得が必要 | 推奨。第1段階の照合結果で確定する |
| Aへのリンクだけを即時に戻す | 接続先変更だけが原因なら短い変更で戻せる | Aの稼働状態や履歴互換性を未確認。別の不具合を再導入する可能性がある | 調査前の実行は不採用。必要な検証を満たした場合だけ採用可能 |
| Bへ回答連携を一から追加する | 管理中のソースへ集約できる | 既存の契約を再実装し、企画や回答を重複生成する危険がある | 現段階では不採用。既存版が復旧不能と証明された場合のみ別途設計する |

## 4. 全体制約

- この依頼で変更するのは本計画書だけ。Apps Script編集、フォーム作成、招待、回答送信、Firebase書込み、push、merge、公開設定変更は行わない。
- 調査結果を得る前に本番URL変更、ロールバック、新しい連携機能の実装へ進まない。
- 実行時はこの端末・このチャットを継続利用する。別デバイスへの引き継ぎを前提にしない。
- 企画ツールの既存変更をreset、stash、削除、移動で整理しない。必要な実装は確認した本番基準の別作業領域で行う。
- Carbonの全面再設計、移行ブランチの統合、割当・精算の計算変更は対象外。
- `applicationSync`の独立したデータ所有権、回答ごとの識別キー、参加者確定状態、削除記録、車割り・精算の既存値を守る。
- 認証情報、Firebaseへの書込み権限、作成権限・提出用データの能力トークン、実応募者情報をGit・チャット・スクリーンショットへ出さない。
- 公開時には「フォーム回答連携」「ポータル履歴」「テーマ」「Pages配信」を別々に判定する。どれかの成功で全体完了としない。
- 過去の6luna指定は添付の会話に記録されている。実装再開時に実際の選択モデルを確認し、指定モデルで実行したと偽って報告しない。本計画でモデル切替や別チャット作成は行わない。

## 7. 第3段階: 実際の回答経路を検証する

**実行条件:** 実装の再指示を受けた後、合成データ専用フォーム・専用企画・利用するGoogleアカウント・後片付け方法を確定する。実応募者や実運用フォームへの回答で代用しない。

| 確認項目 | 合格条件 |
| --- | --- |
| フォームと企画の関連付け | 作成したform IDと企画IDの対応が一意。重複した企画を生成しない |
| 新規回答 | 一意なテスト回答が対応企画の応募者一覧へ、手動取込みなしで反映される |
| 回答更新・送信再試行 | 同じ回答の編集と同一イベント再実行で重複応募者を増やさない |
| 企画の分離 | 2つの専用企画へ別の回答を送って混入しない |
| 同名応募者 | 異なる回答IDの同名応募者を1人へまとめない。曖昧な参加者対応を黙って確定しない |
| 参加者確定 | 応募を受信するだけでは参加確定しない。選択・確定後の人数と対象が一致する |
| 車情報・後続業務 | 受信した車種・同乗人数等を既存契約で扱い、既存割当・精算・提出用データを壊さない |
| 再表示・複数端末 | 再読込みと別ブラウザの企画閲覧でFirebase上の応募者が見える。履歴自体は従来どおりブラウザ単位 |
| 履歴・テーマ | 作成フォームと対応企画を開ける。履歴統合、dark/light、親子通信の拒否条件が維持される |
| 権限エラー・送信失敗 | フォーム作成だけ成功した場合に「回答連携成功」と表示しない。トリガー失敗と受信失敗を識別できる |

反映時間は正常版の実測を記録して検証の待機上限を決める。合格記録にはform ID・テスト企画ID・回答識別子・送信時刻・反映時刻を対応付ける。個人情報・能力トークン・秘密値を含めない。

**既存検証との使い分け:**

- ポータルでは `npm.cmd run test:history`、`npm.cmd run build`、`npm.cmd run test:browser`、`node tests/portal-history-origin-smoke.cjs`、`node tests/deployment-contract.cjs` を変更範囲に応じて実行する。これらだけでは実Googleフォームの送信処理を検証できない。
- 企画ツールを変更する場合は、該当ownerの単体テストとEmulator・対象ブラウザシナリオから始める。本番リリース時の全体ゲートは既存のリリース手順に従う。
- 新しく必要なのは「実Googleフォーム → 既存送信処理 → Firebaseの対象企画 → 応募者画面」の証拠。モックの成功応答やサンプル応募者の表示をその代用にしない。
- UIを変更した場合はdesktopと390px、キーボード操作、表示状態、横overflowを実画面で確認する。

## 9. 完了の定義と次の着手点

完了は、正しいフォームメーカーからテスト用応募フォームを作り、回答が対応する企画の応募者一覧へ自動反映され、参加者の選択・確定と後続業務が維持された証拠がそろった時点。HTTP 200、履歴準備完了、テーマ表示、build成功だけで完了としない。

**実装の再指示を受けたときの最初の作業は、第1段階のA/B照合。** ソースの取得結果と因果関係を本書へ追記し、最小修正の対象を確定してから第2段階へ進む。

本書作成時点では、計画書以外の変更、Apps Scriptへの接続・編集、フォーム作成、実回答送信、本番書込み、push・公開を行っていない。
