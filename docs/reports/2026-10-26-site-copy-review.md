調査日：2026年10月26日（日本時間）
対象：公開サイトのトップページ、応募フォームメーカー、表示設定
成果物：改善提案。本番画面・アプリのコード・運用設定は変更していない。

## 1. 提案の要点

このサイトに合うのは、サークルの幹事が読んですぐ操作できる、短く具体的な文言です。大きなキャッチコピーや丁寧な説明の追加は必要ありません。操作の対象を明示し、処理の状況と次に押すボタンが一致するように整えるのが効果的です。

優先するのは次の5点です。

| 優先度 | 現在の問題 | 改善方針 |
| --- | --- | --- |
| P1 | 「受付」が、参加者の応募受付ともフォームの作成依頼とも読める | 作成機能については「フォームの作成」「作成依頼」と書く |
| P1 | 「画面を閉じても履歴から状態を確認できます」が、現在の履歴表示と合っていない | 作成待ちの状態は「この画面で自動更新されます」と案内する |
| P1 | 結果不明なのに「結果を確認しています」と表示する | 自動確認中と区別し、「作成結果を確認できません」と書く |
| P1 | 「一部の設定を確認してください」だけでは、何が未完了か分からない | フォームの作成と、共有・企画連携などの設定を分けて示す |
| P2 | 「更新」「もう一度お試しください」など、操作の対象が曖昧 | 「履歴を更新」「作成状況を更新」のように、画面上の操作名を示す |

P1は、誤操作や重複作成につながる説明。P2は、迷いや読み直しを減らす修正。P3は、表記や読み上げの統一です。

ソースの基準は `3bb207d168c7ae9087ca6c94f3bda655d274fabf` です。公開画面の通常文言を照合していますが、配信済みファイルの全バイトがこのコミットと一致することまで認証した調査ではありません。ローカルには既存の未コミット変更があるため、その内容を公開版の根拠にはしていません。

「全文言」は、このリポジトリが管理する2ページの固定文言、動的な文言のひな型、通知、入力エラー、代替表示、読み上げ用ラベル、ページタイトル、検索向け説明を対象にしています。ユーザーが入力した企画名・メールアドレスなどは書き換え対象にしていません。

全件の現行文言・推奨文言・判断・ソース位置は、[文言カタログCSV](./2026-10-26-site-copy-inventory.csv)にまとめています。同じ文言でも管理ファイルが違う場合は別行にしています。内部診断用の文字列も、画面へ直接出す文言と区別して記録しています。

カタログは8ファイル・169レコードです。このうち16レコードは内部診断で、残り153レコードが利用者向け文言・表示候補・メタ情報です。169という数は、変更数や画面上の固有文言数を表すものではありません。

## 3. 文章の基準

### Carbonの公式指針

- UIの文章は、簡潔で、操作につながり、用語が一貫していることを重視する。[Content foundations](https://carbondesignsystem.com/building-blocks/foundations/content/#content-foundations)
- ボタン名で、実行する操作を予測できるようにする。英語の「動詞＋対象」という考え方は、日本語では「対象＋動詞」に置き換える。[Button: Main elements](https://carbondesignsystem.com/building-blocks/core/components/button/guidelines/#main-elements)
- 必須・任意の示し方をフォーム全体で統一する。任意項目の方が多いフォームでは、必須項目に印を付ける。[Forms: Optional vs. mandatory](https://carbondesignsystem.com/building-blocks/core/patterns/forms/#optional-vs-mandatory)
- 通知は状況の変化や操作結果を伝えるために使い、必要以上に増やさない。[Notification: When to use](https://carbondesignsystem.com/building-blocks/core/components/notification/guidelines/#when-to-use)

以上はCarbonの一般的な指針です。以下の日本語や、どの説明を省くかは、このサイトの利用者と実装に合わせた提案です。

### このサイトで採用する書き方

1. サイト名は、指定済みの「山歩会企画ツール一覧」を維持する。4つのツール名も維持する。
2. 見出しやボタンは短く、説明文は「です・ます」で揃える。「可能です」「ご利用いただけます」などに言い換えない。
3. 「確認」「更新」には対象を付ける。エラー後の案内は、実際に押せる操作名と一致させる。
4. フォームを作った人には「作成」、参加希望者には「応募」、企画で参加が決まった人には「参加」を使う。
5. 通常画面でFirebase、要求ID、受付枠、引き継ぎ権限などの内部用語を使わない。必要な診断情報は別に扱う。
6. 履歴の保存範囲、下書きの保存、再作成、所要時間について、実装で保証していないことは書かない。
7. すでに削除を希望された「企画の管理」「履歴」という大見出しや、画面全体を説明し直す一文は追加しない。

| 用語 | 使う場面 | 避ける表記 |
| --- | --- | --- |
| 応募フォーム | 参加希望者が回答するGoogleフォーム | 「フォーム」だけで回答用・編集用が混ざる表記 |
| フォームの編集 | Googleフォームの編集画面を開く操作 | 「編集用」を対象なしで使う表記 |
| 企画 | サークル企画ツール内の企画 | 通常画面での「ルーム」「room」 |
| 作成依頼 | フォーム作成ボタンを押して処理を依頼した状態 | 対象が分からない「受付」「申込み」 |
| 作成待ち／作成中 | 処理待ち／実際の作成処理中 | どちらにも「作成中」を使う表記 |
| 作成状況 | 作成待ちから完了までの状態 | 「履歴」との混同 |
| 作成履歴 | 作成結果の一覧 | 全端末・全利用者の一覧だと受け取れる説明 |

| 状態 | 現在 | 推奨 |
| --- | --- | --- |
| 接続確認中 | 受付状況を確認しています | フォームを作成できるか確認しています |

| 停止・本文 | 入力内容は入力できます。受付再開後に作成できます。 | 時間をおいて、もう一度このページを開いてください。 |
| 接続失敗・見出し | 受付状況を確認できません | フォーム作成サービスに接続できません |

「状態を再確認」は既存の再取得処理を呼ぶ操作の追加案です。本文にこのボタン名を書く場合は、同時にボタンを配置します。入力内容はReactの状態にあり、ページ再読み込み後の復元は保証されていません。下書きが残ると案内する変更は採用しません。

## 7. 作成依頼後の表示

| 状態 | 推奨見出し | 推奨本文 |
| --- | --- | --- |
| 作成待ち | 作成待ち | 作成の順番を待っています。始まるまで数分かかることがあります。状態はこの画面で自動更新されます。 |
| 作成中 | 作成中 | 作成が終わると、この画面にリンクが表示されます。 |
| 完了 | フォームを作成しました | 応募用リンクを参加希望者に共有できます。 |
| 一部完了 | フォームは作成済みですが、設定が一部未完了です | 未完了の項目を下に表示する。共有・回答シート・企画作成・応募連携のうち、実際の結果に合わせる。 |
| 失敗 | フォームの作成を完了できませんでした | 再作成する前に、作成したフォームの一覧を確認してください。 |
| 結果不明 | 作成結果を確認できません | 重複を防ぐため、新しく作り直さず「作成状況を更新」を押してください。 |

「失敗」の行は、フォームが絶対に存在しないことまでフロントエンドで確認できていない場合の保守的な表現です。「フォームは作成されませんでした」と断言するには、バックエンドの状態定義との照合が必要です。

一部完了では、表示できる情報に応じて、たとえば「編集権限の共有が完了していません」「回答シートの設定が完了していません」「企画との連携が完了していません」のように具体化します。単なる「確認してください」で終わらせず、対応可能な操作・連絡先が決まった項目から案内を追加します。存在しない「設定を修復」「再試行」ボタンは文言だけで約束しません。

「申込みが混み合っている」とは限りません。現在の予約処理は権限関連の拒否も次の枠へ進めるため、上限まで失敗したという情報だけで混雑と決めつけない方が正確です。

また、送信結果が不明なエラーに、一律で「もう一度作成してください」と書く案は採用しません。フォームがすでに作られている可能性があるため、先に状況を照会する案内にします。

## 11. 文言だけでは直らない項目

| ID | 優先度 | ソースから分かったこと | 提案の適用条件 |
| --- | --- | --- | --- |
| R1 | P1 | 作成中のIDは `sessionStorage` に保存。履歴への変換は `completed` と `partial` のみ | 画面を閉じても「状態を確認できる」と約束するなら、未完了ジョブの一覧・再表示を実装する。文章だけ先に直すなら、この約束を削除する |
| R2 | P1 | 自動照会は `queued` と `running` のみ。`unknown` は自動照会されない | 結果不明に「確認しています」と書かない。現在ある「作成状況を更新」を案内する |
| R3 | P1 | 送信失敗でIDだけが残ると、`pendingId` によって主ボタンが無効になることがある | エラー欄から状況を再取得できる操作を設ける。再作成を指示するだけでは解消しない |
| R4 | P1 | 一部完了の `stepResults` は保持するが、現在の結果欄では詳細を表示しない | 未完了の処理を表示する。修復操作がない項目について、修復できると書かない |
| R5 | P1 | `failure.message` がそのまま表示される経路に英語のFirebaseエラーが入る | エラーの種類と送信段階に応じたユーザー向け表示へ変換する。内部エラーをすべて同じ「再作成」で処理しない |
| R6 | P2 | トップページの「もう一度読み込む」はローカル履歴の再読込。サーバーのジョブ再取得はその操作では行わない | フォーム履歴を再取得できるようにしてから「履歴を読み込み直す」を回復操作として案内する |
| R7 | P2 | フォームページは `historyState=loading` でも、空の説明を表示し得る | 読み込み中と空を分けてから、空表示の文言を使う |
| R8 | P2 | `refresh()` は履歴と作成サービスの確認をまとめて処理し、失敗すると作成ボタンも止まり得る | 「入力画面はそのまま使えます」という案内を削除。必要なら履歴の失敗と作成可否の状態管理も分ける |
| R9 | P2 | 企画名とメールアドレスは `required`、他3項目は任意 | 見える必須表示も付け、読み上げ時の必須状態を維持する |
| R10 | P2 | トップページの編集リンクは、開く操作がなくコピーだけ | コピー失敗時に開く操作を案内するなら、同じ対象を開くリンクを用意する |

これらは文章の監査で見つかった、案内と動作を合わせるための課題です。このレポートの作成中には実装していません。

## 12. 採用しない変更

- サイト名やツール名を全面的に改称する。既存の呼び方とリンクの用途を優先する。
- 「企画の管理」「履歴」といった大見出しや、削除済みの全体説明を戻す。
- 「すべて自動」「必ず反映」「最大5分」「画面を閉じても安心」など、保証範囲を広げる文章を足す。
- 全ボタンの「作る」を機械的に「生成」にする。「生成」はこのサイトでは不要。
- 入力エラーを一律の「エラーが発生しました」にまとめる。直す項目が分からなくなる。
- 応募フォームを開くだけの操作を「応募者を確認」と書く。応募者一覧を開く操作ではない。
- 企画名や匿名利用者のIDなど、保存されたユーザーデータを文章の統一目的で変更する。

## 13. 適用する場合の順序

1. P1の誤解を生む説明を直す。「受付」の対象、閉じた後の追跡、結果不明、一部完了を優先する。
2. R3〜R5の回復操作と結果表示を整え、エラー時の文章を実際の操作に合わせる。
3. 入力ラベル・必須表示・履歴・コピー操作・空表示を揃える。
4. カード説明、表示設定、日時、読み上げ名、HTMLの代替表示を揃える。

文章の差し替えだけを先に行う場合も、R1・R2のような誤った約束の削除は先行できます。存在しないボタン名を本文に入れる変更は、そのボタンを追加する変更と同時に行います。

適用後は、通常表示だけでなく、停止・接続失敗・作成待ち・結果不明・一部完了・コピー失敗・履歴なしを確認します。スマートフォンの幅でラベルが切れないこと、読み上げ名と見えるボタン名が一致することも確認対象です。現時点では提案のため、変更後の表示確認や本番への反映は行っていません。
